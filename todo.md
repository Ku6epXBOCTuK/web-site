# 📋 Финальный план реализации процесса (без кода)## Этап 1. Подготовка инфраструктуры в Git

- [ ] Создание изолированной ветки: Создать в репозитории пустую ветку-сироту (posts_db), которая будет служить базой данных.
- [ ] Инициализация файла БД: Добавить в корень этой ветки один пустой файл posts.yaml для хранения связок ID и сохранить изменения.
- [ ] Настройка секретов: В настройках репозитория на GitHub добавить токены авторизации для Telegram и Discord.

## Этап 2. Проектирование триггеров и окружения в GitHub Actions

- [ ] Настройка фильтра запуска: Задать активацию workflow только при пуше в ветку main и только при изменениях внутри папки со статьями.
- [ ] Загрузка базы данных: Добавить шаг, который перед стартом основного скрипта скачивает актуальный файл posts.yaml из ветки posts_db.
- [ ] Сбор и передача изменений: Настроить получение списка всех добавленных и измененных файлов статей в текущем коммите для передачи в скрипт.

## Этап 3. Валидация и логика работы скрипта

- [ ] Проверка количества файлов (Строгий фильтр):
  - [ ] Если файлы статей не менялись — скрипт успешно завершает работу.
  - [ ] Если изменилось более одной статьи — скрипт намеренно аварийно завершается с понятной ошибкой в логах.
  - [ ] Если изменилась ровно одна статья — она передается в следующий шаг.
- [ ] Парсинг текста: Извлечь содержимое этой единственной статьи и очистить его от технических метаданных (Front Matter).
- [ ] Проверка по базе данных (Ветвление): Изучить скачанный posts.yaml на предмет наличия пути к этой статье.
- [ ] Сценарий А: Новая статья (Путь в БД отсутствует):
  - [ ] Отправить текст в Telegram и Discord.
  - [ ] Дождаться ответа от платформ и забрать ID созданных сообщений.
  - [ ] Записать эти ID в объект базы данных под ключом пути к файлу.
- [ ] Сценарий Б: Редактирование (Путь в БД найден):
  - [ ] Извлечь сохраненные ID для Telegram и Discord.
  - [ ] Пытаться вызвать методы редактирования на обеих платформах.
  - [ ] Обернуть вызовы в обработчики ошибок: если пост удален в соцсети или время редактирования истекло, зафиксировать это в логах и продолжить выполнение (пропуск шага).

## Этап 4. Фиксация результатов

- [ ] Сохранение состояния: Записать обновленный объект базы данных обратно в файл posts.yaml.
- [ ] Скрытый коммит: Настроить финальный шаг GitHub Actions, который отправляет измененный posts.yaml строго обратно в ветку posts_db, оставляя историю ветки main абсолютно чистой.

## Этап 5. Тестирование

- [ ] Проверка защиты: Попробовать запушить две статьи одновременно и убедиться, что экшен заблокировал процесс.
- [ ] Проверка создания и редактирования: Поочередно запушить одну новую статью, а затем её измененную версию, проверяя корректность постов в соцсетях и чистоту истории коммитов в main.
